# 自動スケジューリングの決まりごと

Study Check は、その日に取り組む問題をロジックで決める。AI は使わない。

同じ学習状態なら、いつ何度動かしても同じ予定になる。だからバグを再現でき、
自動テストで確かめられ、オフラインでも動き、なぜその問題が出たかを説明できる。

このファイルは「何をどう決めているか」を1か所にまとめたもの。
実際の判断は `src/mastery.js` / `src/review.js` / `src/auto-plan.js` にあり、
テストは `test/mastery.test.mjs` / `test/review.test.mjs` / `test/auto-plan.test.mjs`
/ `test/plan-changes.test.mjs` にある。

## 役割の分け方

| ファイル | 役割 |
|---|---|
| `src/mastery.js` | 評価の履歴から、その問題が今どういう状態かを決める |
| `src/review.js` | 次にいつ復習するか・どれくらい急ぐかを決める |
| `src/auto-plan.js` | 1日ぶんの予定を組み立てる（全体の入口） |
| `src/plan-changes.js` | 作った案を当ててよいか確かめる |
| `src/auto-plan-runner.js` | IndexedDB から読み、確かめてから書く |
| `src/settings-auto-plan.js` | 設定タブの画面 |

`mastery.js` / `review.js` / `auto-plan.js` / `plan-changes.js` は純粋な処理である。
IndexedDB も画面も時計も触らない。入れたものが同じなら、出てくるものも必ず同じになる。

## 基本の考え方

アプリの役割は**学習の事実を保存すること**、スケジューラの役割は**その事実から
次に何をすべきかを決めること**。この2つを混ぜない。

計画と実際の記録は別物である。予定した問題をやらなかったとしても、それを
「間違えた」とは扱わない。その問題の状態を決めるのは、実際に記録された評価だけ。

## 動く順番

```
現在の学習状態を取得
   ↓
未完了タスクを確認
   ↓
復習候補を生成
   ↓
各問題の習得状態を判定
   ↓
復習優先度を決定
   ↓
新規問題候補を生成
   ↓
目標 priority を考慮
   ↓
利用可能時間へ配置
   ↓
既存スケジュールとの差分を生成
   ↓
変更内容を検証（validatePlanChanges）
   ↓
安全なら適用（applyPlanChanges）
   ↓
適用後の状態を再確認（verifyApplied）
```

**1問につき1タスク**を基本単位とする。

## 評価

| 値 | 意味 | 扱い |
|---|---|---|
| `perfect` | 十分に理解し、正しく解けた | 復習優先度は大きく下がる |
| `better_solution` | 正解だが、より良い解法がある | 重大な弱点ではない。軽い復習 |
| `calc_error` | 考え方は合っているが計算ミス | 軽度の弱点 |
| `weak_writing` | 考え方は分かるが記述が弱い | `calc_error` と同じ重さ |
| `wrong_approach` | 解法方針そのものが違った | 最も重要な復習対象 |

評価が未登録の記録は、正解にも不正解にも数えない。
「解いたけれど評価を入れていない」を弱点として扱うと、事実でないものを作ってしまう。

## 習得判定

`perfect` 1回では完全習得とみなさない。

- `perfect` が**2回**そろった時点で「**一応クリア**」
- そのあとに `wrong_approach` / `calc_error` / `weak_writing` / `better_solution` の
  いずれかが記録されたら、クリアを解除する

```
wrong_approach → perfect → perfect → クリア
perfect → perfect → wrong_approach → クリア解除
```

クリアを解除したときは、`perfect` の数え直しも行う。
これをしないと、一度クリアした問題は間違えたあと `perfect` 1回でクリアに戻ってしまい、
上の1つ目の例（間違えたあとは `perfect` 2回が要る）と食い違う。

## 復習周期

復習は新規学習より必ず優先される。

| 直近の評価 | 次の復習まで |
|---|---|
| `wrong_approach` | 次の学習日。繰り返しても短いまま |
| `calc_error` / `weak_writing` | 3日後。同じ弱点が続くと 3日 → 2日 → 翌学習日 と縮む |
| `better_solution` | 5日後。復習はするが急がない |
| `perfect`（まだクリアでない） | 7日後。2回目の `perfect` を取りに行く |
| 一応クリア | 通常フェーズでは復習に出さない |

「最近の履歴を優先する」とは、**同じ弱点が続いた回数**で縮めるということである。
遠い昔に1度あった計算ミスで、いまの周期を短くはしない。

予定日を過ぎていても「遅れた」とだけ扱い、間違えたことにはしない。
遅れが大きいものほど先に出す。

## 復習の優先順位

```
方針の弱点（wrong_approach）
   ↓
計算・記述の弱点（calc_error / weak_writing）
   ↓
より良い解法（better_solution）
   ↓
まだクリアしていない問題
   ↓
一応クリアした問題の維持復習
```

`perfect` になった問題を機械的に何度も復習させない。
ほかに弱点が残っているあいだは、そちらを優先する。

## 維持フェーズ

対象範囲の問題がすべて一応クリアしたら、**維持フェーズ**へ移る。
維持フェーズでは全問を繰り返さず、代表的な問題だけを間を置いて復習する。

残すもの:

- 過去に2回以上つまずいた問題
- `wrong_approach` を2回以上経験した問題
- 一度クリアしたのに評価が崩れた問題（安定しなかった問題）
- 少し応用的な問題（重要例題・演習例題・EXERCISES、または難易度4以上）

外すもの:

- 簡単で、ほとんど失敗せず、安定して `perfect` だった基本問題

問題どうしのつながり（この例題の考え方を使う応用問題か）は、このアプリの問題マスタでは
分からない。代わりに、誌面で応用側に置かれている種類と難易度を手がかりにする。
推測で関連を作って理由に書くことはしない。

## 新規問題の順番

新規問題は**教科書の掲載順**を必ず守る。スケジューラの都合で好きな問題から進めることはしない。

```
90 → 91 → 92 → 93
```

途中に復習問題を挟むのはよい。

EXERCISES は通常の新規問題とは別に扱う（→ チャレンジ）。

## 目標 priority

目標の priority は点数ではなく**学習段階**として扱う。

新規学習は、まだ手つかずの問題が残っている中で、いちばん priority の小さい段階からだけ出す。
priority 3 が残っているうちは、priority 4 の**新規問題**には進まない。

ただし priority は**新規進行だけ**を制御する。必要な復習は妨げない。

```
priority 4 の復習 ＋ priority 3 の新規学習   … 許可する
priority 3 が残っているのに priority 4 の新規問題 … 出さない
```

その段階に未着手の問題がもう無いときは、次の段階へ進む。
そこに新規問題が存在しない以上、待っても何も出てこないためである。

## 復習と新規問題の配分

1日の学習可能時間が足りない場合、**復習を優先する**。

復習予定だけで枠が埋まるなら、その日の新規問題は0問でよい。
「毎日最低1問は新しい問題を進める」といった固定ルールは設けない。

## 時間の見積もりと容量

問題ごとの予想所要時間から、1日の学習量を決める。見積もりの元は上から優先する。

```
manual → history → history_blended → similar → ai_estimate → default
```

本人の十分な履歴があれば、一般的な推定より本人の最近の安定した履歴を優先する。
1回だけ極端に長かった記録には過剰反応しない（平均ではなく中央値を使い、
数秒で終わっている記録や長すぎる記録は計算から外す）。

見積もりの確からしさで、その日に使う枠の割合を変える。

| 確からしさ | 使う割合 |
|---|---|
| high | 95% |
| medium | 90% |
| low | 80% |

実際の割合は、その日に置いた問題の確からしさの混ざり具合から決まる。
埋めきってしまうと、少しの読み違いで大量の繰り越しが出るためである。

**未設定の日と0分の日は別物**として扱う。どちらにも予定は置かないが、
未設定の日は「時間があるかどうか分からない」であって、「0分」ではない。

## 未完了タスク

予定した問題をやらなかったとしても、失敗とはみなさない。

- 元の予定項目のまま翌日以降へ繰り越す（`itemId` を変えない）
- 新しい同じタスクを作り直さない
- 繰り越しても取り組み回数は増えない
- 未完了の理由（時間不足・難しかった など）を自動で推測しない。単に「未完了」として扱う

繰り越しは、その日のいちばん先に置く。

## 期限

目標の期限は重要な制約として扱う。ただし、期限に間に合わせるために必要な復習を飛ばすことはしない。

期限までの容量が足りない場合でも、次のことは**しない**。

- 期限を勝手に延ばす
- 目標範囲を狭める
- 習得条件を弱める
- 学習に使える時間を勝手に増やす

足りないという事実だけを知らせる。どうするかは利用者が決める。

## チャレンジ

EXERCISES などのチャレンジ問題は、通常の新規問題とは別に扱う。

章内の例題が必要な習得状態に達したら `challenge ready` と判断する。
ただし**チャレンジの中身は自動で決めない**。何をどれだけ、どの難易度で解くかは利用者が選ぶ。

```
HUMAN_INPUT_REQUIRED: challenge ready
```

## 安全なスケジュール更新

自動プランナーは直接スケジュールを書き換えない。必ず
「現在状態取得 → 変更案生成 → 検証 → 適用 → 状態再取得 → 結果確認」を通る。

次のものには手を触れない。

- いま解いているタスク
- 完了したタスク
- 固定（ピン留め）したタスク
- 利用者が自分で入れた予定（自動で置いた印 `source: "auto"` が無いもの）
- 過ぎた日の予定

同じ自動計画が複数回実行されても二重に当たらないよう、**安定した operationId** を使う。
これは案の中身と、当てる先の日の版（revision）だけから決まる。乱数も時刻も混ぜないので、
状態が変わっていなければ必ず同じ値になり、当てたことを覚えておくだけで二重適用を防げる。

危ないものだけを落とし、残りは通す。落としたものは理由つきで画面に出す。

## この方式にした理由

スケジューラの判断が予測可能になること。同じ学習状態なら、基本的に同じ予定が生成される。

- バグを再現しやすい
- 自動テストを書きやすい
- 出力が揺れない
- 外部サービスの障害にも、通信状況にも左右されない
- 費用がかからないので、誰にでも配れる
- なぜその問題が予定されたか説明できる
